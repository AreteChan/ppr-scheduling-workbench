口径规则
目标层级① 满足交付 → ② 需求优先级（第一顺位硬约束）→ ③ 开机机台 / 产线台数最少 → ④ 总损失时间最小 → ⑤ 切换次数最少 → ⑥ OEE 平级择优。第 ③ 层为 v0.9.2 新增：少开机台 ＝ 少投操作工、少摊开机与看护成本；「换型次数」与「OEE」仍是平级参考（统计 / 展示 / 导出照旧保留）。
总损失时间Σ 普通换型停机分钟 ＋ Σ 首块 D-1 新开机 ＋ Σ 空闲重启 D-1；废品 kg 只作参考展示、不折算进排序（换算系数固化 ＝ 0）。
机台负荷率（逐台）(生产 ＋ 普通换型 ＋ 首块 D-1 ＋ 空闲重启 D-1) ÷ 可用分钟；＜ 95% 绿（正常）/ ≥ 95% 黄（接近满负荷）/ ＞ 100% 红（超载）。
整体负荷率（已开机台）Σ(已开机台 生产 ＋ 普通换型 ＋ 首块 D-1 ＋ 空闲重启 D-1) ÷ Σ(已开机台 可用分钟)。与「产能利用率（全厂）」不是一回事：分母只算本周期真有排程的机台，用来判断「开出去的机台有没有被开满」。参考目标 ≥ 80% 且 ＜ 100%；开机台数越少、整体负荷率越高 ＝ 越省操作工。指标看板与排程视图右侧 KPI 都可见。
超载软约束 —— ＞ 100% 只弹窗提示并写进「数据体检」，不阻塞提交；先保交付，由你决定是否调机台 / 增补班次。
不停机为原则停机后重新开机次数 ＝ 段数 − 1（空档扣除该处换型占用后仍有 > 1 分钟真实空闲才算，换型时间不重复计入）。
D-1「新开机」判定（v0.9.3 连续性）该机台上周不在产，或上周末块提前收工（没一直做到本周期开始 · 中间停过） → 本周首块前计一次 D-1（90 分钟 / 80 kg）；只有连续在产到本周期开始才不计。逐台判定在「上周开机情况确认」核实，可人工覆盖。
触发方式只有显式点「重新优化」才重排；拖动调整后不会自动重排。
需求优先级（＝计划交期替代）第一顺位硬约束（v0.9.1）：需求表自带「优先级」升序先排，再在这个框架内做损失优化；局部改进不得跨优先级倒挂，倒挂会被全量校验报红牌、不允许带错提交；同一优先级内 / 未填时退回归簇 → 交期 → 大单 → 行号。
周口径周日 00:00 起、周期 168 h（W40 ＝ 2026-10-04 ~ 2026-10-10）；休日 ＝ 不可生产，拖入会被拦截。

  • 要修的问题：v0.7.1 起的判定口径是「本周新开机 ＝ 该机台上周不在产（上周存档里没有任何计划块）」。这只看了「上周排没排过块」，没看有没有连到本周 —— 某台机上周排完两三天就停了、本周期才重新开机，按旧口径会被判成「不算新开机」，D-1（90 分钟）就漏计了。用户 2026-10-15 定的口径：只有「上周持续在产、连续到本周」才不计 D-1；中间中断的算新开机。（首周 / 无历史不受影响，从第二周滚动开始才会显形。）

  • 确认页看得见：第 4 列列头改为 「上周计划块 / 数量 / 末块结束」，逐台显示末块结束时间并标注 （做到周界）/（已停 → 中断）/（上周无块）；「判定来源」列区分 存档·连续 / 存档·中断 / 旧快照 / 无历史 / 人工改；有中断台时弹窗顶部单独提示「上周末块提前收工 → 已按本周新开机预填，若实际是连续在产请点回去」。

v0.9.22026-10-15v0.9.2 新增（2026-10-15）：目标层级补上「开机机台 / 产线台数最少」＋ 整体负荷率（已开机台口径）
  • 为什么要补这一层：只压「总换型损失时间最小」时，求解器会把需求摊到 10 台机台上、每台负荷只有 15% 左右 —— 交付没问题，但开出去的机台太多，操作工与看护成本翻倍。用户 2026-10-15 指出：要用最少的机台 / 产线把交付做完，因此这层是硬性的 第 ③ 层目标。
  • 目标层级（现行）：① 满足交付 → ② 需求优先级（第一顺位硬约束）→ ③ 开机机台 / 产线台数最少 → ④ 总损失时间最小 → ⑤ 切换次数最少 → ⑥ OEE 平级择优。
  • 落地四段（纯本地启发式，不用任何求解器 / API）：[1] 从「零开机」出发、带「新开机台绝对惩罚」的贪心（能塞进已开机台就不新开）；[2] 交付兜底＝按需逐台追加开机（还有欠交就挑一台最能吃掉欠交量的机台，欠交变少才收下，逐台追加到 100% 交付）；[3] 仍欠交才与「不惩罚」解比字典序（欠交量 → 机台数）；[4] 剔台收敛（仅当已 100% 交付）：逐台试剔，只用「剩下的机台」整单重排，仍 100% 交付才收下 → 机台数局部最小。最后仍由局部改进继续压第 ④ 层。
  • 整体负荷率（新指标）：Σ(已开机台 生产 ＋ 普通换型 ＋ 首块 D-1 ＋ 空闲重启 D-1) ÷ Σ(已开机台 可用分钟)。分母只算真开机的机台，与「产能利用率（全厂）」并列展示；指标看板有专卡专行，排程视图右侧 KPI 与逐台负荷率面板顶部也有。
  • 真实数据实测（天津周计划需求 / 产能数据 / 日历）：开机机台 10 台 → 3 台（共 15 台）、欠交 0 行、整体负荷率 15.8% → 54.6%；代价是换型损失 115 min → 455 min。实测 2 台不可行（只能交付 92,860 / 119,472 kg）。取舍由计划员定：要更少开机台，就得接受更多换型损失；不满意可关掉 ⑥ 卡里的「③ 优先：开机机台 / 产线台数最少」再点「重新优化」。
  • 未改动：15 条硬约束、优先级第一顺位、拆分上限、压实口径、「拖动后实时校验 + 只有点『重新优化』才重排」的分工，一行未改。

⑦ 一个必须说清的判断

如果这个 API 背后是大模型，不建议让它直接决定"哪个任务排哪台机、什么顺序"。原因：结果不可复现（同样输入两次不同答案）、硬约束会漏（撞机台、漏换型占位）、数量会算错。建议 API 后端用确定性算法（CP-SAT 或自建启发式），大模型只做自然语言录入与解释。详细论证见《技术方案 v2》第 3 节。

本地启发式的作用就是兜底：没网、API 挂了、API 结果可疑时，你手上永远有一个能出计划、且同一输入永远同一结果的工具。
